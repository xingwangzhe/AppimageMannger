# Linux packaging

The application and all packages use the executable name `appimage-mannger`.
Package builds never need root. Only native-package installation uses the system
package manager and administrator authentication.

```sh
cargo build --release --locked
bun run scripts/package.ts --formats deb
# CI/native runner with rpmbuild installed:
GH_TOKEN="$(gh auth token)" bun run scripts/package.ts --formats deb,rpm,appimage,tar,arch
```

`--binary PATH`, `--arch x86_64|aarch64`, and `--out DIR` are optional. Architecture
must match the current native runner. Build x86_64 and ARM64 separately. Debian
packages use `amd64`/`arm64`; RPM, AppImage and portable archives use
`x86_64`/`aarch64`.

## CI and publishing

`.github/workflows/linux.yml` runs on pushes to main, pull requests, version tags,
and manual dispatches. Both architectures run tests and Clippy, build optimized
binaries, generate DEB/RPM/AppImage/pacman/portable tar packages, install the DEB, and run
the CLI smoke test from the installed binary and AppImage. The assembly job adds
source archives, AUR source/binary recipes, and `SHA256SUMS`. Checksums are verified
before upload. Tag `v<exact Cargo.toml version>` to publish a GitHub release. A
version containing `-` is published as a prerelease; DEB/RPM encode the separator
as `~`, and Arch/AUR removes prerelease separators (`0.1.0rc1`). Manual publishing requires the existing tag to point to
the checked out commit and to match the manifest version.

The latest GA runners on 2026-10-27 are `ubuntu-26.04` and `ubuntu-26.04-arm`.
These explicit labels avoid `ubuntu-latest` still resolving to Ubuntu 24.04 during
GitHub's migration. Stable Rust and Bun resolve to the latest available releases
on every run. GitHub Actions use the latest verified release versions, with core
checkout/artifact/setup steps pinned to immutable commits. Dependabot checks
Actions and Cargo weekly.

## AppImage and distribution compatibility

AppImages bundle the executable's dynamically linked dependency graph and XKB
keyboard data. The host supplies glibc, graphics drivers, and fonts. The official
latest `AppImage/appimagetool` release is resolved at build time and its downloaded
asset must match GitHub's SHA-256 digest. CI supplies `GH_TOKEN` automatically;
local builds may supply a token to avoid anonymous GitHub API rate limits.
`.build-info.json` records the exact tool digest, bundled libraries, and glibc
build version. Build and smoke tests use `APPIMAGE_EXTRACT_AND_RUN=1`, so they do
not need a FUSE mount.

**Latest-runner builds require a comparably recent glibc.** They are not promised
to run on older Ubuntu/Debian/RHEL releases. DEB dependencies are generated by
`dpkg-shlibdeps`; RPM uses rpmbuild's ELF automatic requirements. Portable/AppImage
packages do not bundle glibc and have the same minimum glibc as their binaries.
AUR source builds compile against the user's Arch system and avoid this mismatch.
The binary recipe targets current Arch Linux / Arch Linux ARM.

## AUR deliverables

After both native portable archives exist in `dist/`:

```sh
bun run scripts/package-aur.ts
bun run scripts/package-checksums.ts
(cd dist && sha256sum -c SHA256SUMS)
```

The result includes a Git source archive and two AUR-ready recipe tarballs,
`appimage-mannger-<version>-aur.tar.gz` and
`appimage-mannger-bin-<version>-aur.tar.gz`. Each contains `PKGBUILD` and `.SRCINFO`.
Source and binary downloads use real SHA-256 sums; no `SKIP` checksums are used.
The source recipe fetches locked Cargo dependencies during `prepare()`, then
builds and tests offline. The recipes are release assets; uploading them to
`aur.archlinux.org` requires a separate AUR account and SSH credentials and is not
done by the GitHub workflow.

## Native pacman binary packages

`--formats arch` produces real `appimage-mannger-<pkgver>-1-<arch>.pkg.tar.zst`
archives, separate from AUR recipe tarballs. They contain executable files plus
standard `.PKGINFO`, `.BUILDINFO` and compressed `.MTREE` metadata. The glibc
minimum comes from the ELF GLIBC symbol-version requirements, not an assumed
distro version. The generated prebuilt-assembly recipe is hashed in BUILDINFO;
the build tool is explicitly recorded as the Ubuntu/Bun native build pipeline,
not falsely described as a build performed on Arch. No AUR account, repository,
or AUR helper is needed to install the downloaded file:

```sh
sudo pacman -U ./appimage-mannger-*.pkg.tar.zst
```

CI checks metadata and file lists with pacman on both architectures, then uses
the official `archlinux:latest` x86_64 Docker image to install the package and
run CLI smoke tests. ARM64 receives native build plus pacman metadata validation;
an ARM Arch container install test is not claimed.

Arch versions use `0.1.0rc1` for `0.1.0-rc.1`: verified using libalpm vercmp
to sort before `0.1.0`, so a stable release upgrades naturally.

## Native Qt and GTK frontends

Every package includes `/usr/lib/appimage-mannger/frontend-qt` and
`frontend-gnome` exported by the matching Rust engine. Packaging refuses
to continue if either helper is missing. DEB dependencies are computed across
all three ELF executables and additionally require the Qt XCB/Wayland plugins.
RPM includes the helper directory and uses automatic ELF requirements.
Arch and AUR runtime dependencies include Qt6 Base/Wayland, GTK4, libadwaita and
JSON-GLib; AUR source recipes export helpers after compilation and the binary
recipe installs the helpers from the native portable archive.

AppImages additionally bundle the three ELF dependency graphs, Qt platform and
image plugins, Wayland/XCB integrations, GSettings schemas, Dconf/GIO and
GdkPixbuf image loaders, Adwaita icons, shared MIME data, the Vulkan loader and
unsquashfs. A relocatable AppRun sets their lookup paths and creates then removes
a temporary image-loader cache. Host libc, fonts and GPU drivers remain external.

For a fully offline local AppDir assembly/inspection, without contacting GitHub:

```sh
bun run scripts/package.ts --formats deb,appdir
```

`--work-dir PATH` can isolate packaging verification from another local build.
CI configuration installs the native development libraries and starts both
installed helpers under Xvfb as an additional toolkit startup check.

## License retention and source traceability

Project metadata uses **AGPL-3.0-only** in native package metadata and both AUR
recipes. This is the owner's choice; it does not relabel Qt, Ely, GTK or another
dependency. Native packages retain the project AGPL text, Ely's original MIT
copyright and full license, the dependency-notices guide, and an inventory of
target-resolved Cargo dependency records with their available original
license files. The inventory states when a registry publisher omitted a separate
license document; it is not presented as a complete legal audit.

For an AppImage, every copied system ELF, Qt/GIO/GdkPixbuf plugin, tool and asset
package is resolved through dpkg ownership. Packaging retains that exact Ubuntu
package's complete copyright file plus all referenced shared GPL/LGPL/Apache and
other common license texts. It fails if a redistributed file's owner or copyright
cannot be identified. `bundled-system-libraries.json` records the binary package,
version, architecture, source package/version, upstream source metadata and
matching `apt-get source` command. Corresponding source availability and any
additional obligations must be evaluated against the exact terms; provenance
records are not a blanket compliance guarantee.

All retained texts and inventories are under
`usr/share/licenses/appimage-mannger/`. AppImage `.build-info.json` points to this
inventory and reports the number of traced system files and packages. Native
DEB/RPM/pacman packages use distribution-provided dynamic libraries and their
normal distribution notices instead of bundling those libraries.

Packaging checks that the input binary's `--version` matches Cargo.toml and
restricts disposable `--work-dir` paths to repository `work/` subdirectories.
It never accepts `~/Applications` as a scratch directory.
